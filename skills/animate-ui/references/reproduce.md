# Reproduce an animation from a link or a video

The user shows an animation they like (a site, a video, a GIF, a screen recording) and wants it on their component. Copy **only the motion**: which properties move, from where to where, for how long, on which curve or spring, in which order. Their component keeps its own look (colors, sizes, radius, type, layout, content) unless they ask for that too.

1. **Read the motion.**
   - A file or a snippet: read its CSS and JS directly.
   - A link: open it in a browser tool when there is one and read what drives the animation: CSS `transition`, `animation` and `@keyframes`, inline Motion or GSAP props in the scripts, or `element.getAnimations()` (keyframes, `duration`, `easing`) while it plays. Trigger it the way a user would (hover, click, scroll). A page that can't be opened: ask for a recording.
   - A video or GIF: look at it frame by frame (extract them at the video's own rate, `ffmpeg -i in.mp4 frame_%03d.png`, when available, and view them; resampling adds duplicate frames). Note each moving element's properties (position, scale, rotation, opacity, blur, clip), start and end values, when each one starts and ends (frame count ÷ fps), and whether it goes past its end and comes back (a spring) or eases in (a curve). To measure rather than eyeball, dump raw frames (`ffmpeg -i in.mp4 -f rawvideo -pix_fmt rgb24 -`), track each element's bounding box and center per frame (the center isn't fooled by a blur widening the box), and fit the curve or spring to those points. Recordings repeat frames (two identical frames are one), and an element fading in from 0 is invisible for its first frames: its real start sits further out than the first frame you can see, so extrapolate it.
2. **Translate it.** The role is the target's (a modal's tokens for a modal). A curve is within 10% of a token's when each `cubic-bezier` control point is within 0.1 of it. A measured value within about 10% of a token made for the same role (a surface's blur, a press's scale, a toast's spring) uses the token: it stays coherent with the rest of the app. Otherwise keep the measured value: the user asked for that animation. Write a spring as `{ type: 'spring', visualDuration, bounce }` (`visualDuration`: when it looks settled; `bounce`: how far it goes past, about 0.1 for a barely visible overshoot, 0.3 for one of about 5% of the travel, 0.5 for a clear bounce back), a tween as its duration and `cubic-bezier`, and pass both through `useTempoTransition()` so `tempo` paces them like the tokens. Offsets between properties (the movement starting 100ms after the fade) are part of the motion: keep them.
3. **Apply the rules anyway.** It gets a reduced-motion path, animates `transform`, `opacity` and `filter` (a reference moving `top` or `width` becomes a transform or a `layout` animation), and stays interruptible. A reference that breaks one (an ease-in entrance, a hover scale on a button) is reproduced as asked; say in the output what the rule would change.
4. **Fill in what the reference doesn't show** from the matching recipe (a toast's exit, a menu's exit; the reference wins over the recipe's own entrance, and the catalog step is skipped), or else by replaying the entrance (B5); and reduced motion from the rules.
5. **Output** what was measured (properties, durations, curve or spring), which values became tokens and which stayed measured, and what wasn't visible in the reference (the exit, reduced motion) and how it was filled in.

## Measuring tips

- **Frame times.** A 25 fps source in a 30 fps file repeats every sixth frame: drop the repeats and count the real frames (40ms each at 25 fps).
- **Blur.** Measure it on a sharp edge with no text: the 10–90% width of the edge's ramp ÷ 2.56 is the blur's radius (σ), which is CSS's `blur()` value.
- **Start times.** An element fading in from 0 is invisible for its first frames, so its movement seems to start later than its fade. Before keeping an offset between the two, fit the motion both ways (starting with the fade and later); keep the offset only if starting together fits clearly worse, and say which you chose.
- **A spring against a token.** Compare natural frequency and damping, not the numbers as written: a `{ visualDuration, bounce }` spring has stiffness `k = (2π / (1.2 · visualDuration))²` and damping ratio `ζ ≈ 1 − bounce`; a token's `stiffness`/`damping` has `ω = √k` and `ζ = damping / (2√k)`. Within about 10% on both, use the token.
- **Offsets between properties.** Write one transition with a `default` key and one key per property (`{ default: spring, opacity: { duration: 0.3, ease }, filter: { … } }`) and pass it to `useTempoTransition()`: it paces the nested ones too.
- **The exit.** Leave toward the values the reproduced entrance came from (its own scale, blur, distance), on the matching recipe's exit timing (`transition.dismiss` for a toast or a dialog).
